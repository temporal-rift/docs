## Topics

| Topic | Producer | Consumers | Partition key |
|---|---|---|---|
| `game.events` | game-service | timeline-service, read-service | `gameId` |
| `timeline.events` | timeline-service | game-service, read-service | `gameId` |
| `game.commands` | *(no in-workspace producer)* | game-service (`PlayerReconnectKafkaConsumer`) | `lobbyId` or `gameId` |
| `game.events.dlq` | timeline-service, read-service (dead-letter target for their `game.events` consumers after retries are exhausted) | — | `gameId` |
| `timeline.events.dlq` | game-service, read-service (dead-letter target for their `timeline.events` consumers after retries are exhausted) | — | `gameId` |
| `game.commands.dlq` | game-service (dead-letter target for `PlayerReconnectKafkaConsumer` after retries are exhausted) | — | `lobbyId` or `gameId` |

There is one dead-letter topic per source topic, not one shared dead-letter topic — this keeps a parked record on
the same partition number as its source, so an operator can replay one game's parked records in order. All six
topics are created with three partitions and an explicit `retention.ms`, set by `infrastructure`'s `kafka-topics`
Compose job, which runs `provision-kafka-topics.sh`: 7 days for `game.events`/`timeline.events`, 1 day for
`game.commands`, and 30 days for every `.dlq` topic — long enough to investigate a parked poison message.

<Note>
The transactional outbox is a service-owned database table, read by a relay that publishes directly to the domain topics above. The Modulith services use `event_publication`; timeline-service uses its own outbox. See [Outbox Pattern](/architecture/outbox).
</Note>

## Partitioned by gameId

The partition key is always `gameId`. This guarantees all events for a single game arrive at the same partition **in order** — required for correct event sourcing replay in `timeline-service` and correct read model projection in `read-service`.

Processing order is guaranteed within a consumer group. Independent groups can progress at different speeds, so
records that mutate causally dependent state must share one logical consumer.

Timeline-service consumes era initialization, event drafting, action submissions, round closure, resolution, and
lifecycle cleanup through `timeline-service.futureevent.game-events`. Its listener dispatches synchronously to
focused handlers, each committing its record transaction before the next record is processed. A slow
`EventsDrawn` transaction therefore delays the following Stall and round closure instead of making replay discard
their target as unknown. The independent faction-membership projection retains its own group.

Logical idempotency identities are retained when consumer groups change. Replaying retained records under the new
group suppresses already committed effects through the existing `(event_id, consumer)` claims. Deploy the lifecycle
listener and handlers together; do not run the previous lifecycle listeners alongside the new group.

## Design decisions

<AccordionGroup>
  <Accordion title="One topic per bounded context, not one per event type">
    Splitting by event type would create hundreds of topics, fragment consumer group coordination, and make it impossible to guarantee ordering across related events for the same game.
  </Accordion>
  <Accordion title="Commands and events on separate topics">
    Commands and events carry different failure semantics and consumer group lifecycles, which justifies keeping
    them on separate topics.
  </Accordion>
</AccordionGroup>

## Consumer requirements

Every Kafka consumer must:

1. Filter unsupported event types and envelope versions before claiming their identities
2. Atomically claim a supported message's `eventId` header in `processed_events` before business work
3. Skip the message when the claim already exists for the same logical consumer
4. Log and skip unknown versions, leaving their identities unclaimed for a compatible replay

Use a service-local `processed_events` table keyed by `(event_id, consumer)`. The claim must be an insert-first
operation such as `INSERT ... ON CONFLICT DO NOTHING`, not an `exists` check followed by a save. If the consumer mutates
state or publishes internal Spring events, the claim and side effects run in the same local transaction.

Same-process `game-service` module handoff uses typed Spring Modulith events. A replay or cross-instance Kafka consumer
for one of those same events is still a Kafka consumer and must use this idempotency guard.
