---
title: "Outbox Pattern"
description: "Atomic write + event publication, no dual-write risk"
---

Every service that writes to the database and publishes to Kafka uses the outbox pattern. It guarantees that aggregate state and events are always consistent — even if the process crashes mid-operation.

## The problem

Without the outbox, a crash between the DB commit and the Kafka publish leaves state updated but event never sent — permanent inconsistency with no recovery path.

## The solution

```mermaid
sequenceDiagram
  participant CH as Command Handler
  participant DB as Database
  participant R as Outbox Relay
  participant K as Kafka

  CH->>DB: BEGIN TRANSACTION
  CH->>DB: Update aggregate state
  CH->>DB: Write outbox record
  DB-->>CH: COMMIT (atomic)
  R->>DB: Poll unpublished records
  R->>K: Publish event
  R->>DB: Mark delivered
```

The aggregate state update and the outbox record are written in **one local transaction**. If the process crashes after the commit, the relay picks up the undelivered record on restart.

## Implementation in game-service

`game-service` uses **Spring Modulith's JDBC event publication table** as the outbox. When a command handler publishes an `ApplicationEvent`, Modulith writes it to `event_publication` transactionally. A background relay reads and forwards to Kafka.

```yaml
spring:
  modulith:
    events:
      republish-outstanding-events-on-restart: false
```

Restart-bound republication is disabled because a restarted instance could replay work that is still being processed by
another live instance. `game-service` instead uses `IncompleteEventPublicationResubmitter` to resubmit publications
that have remained incomplete past the configured minimum age.

<Warning>
**Never call `kafkaTemplate.send()` from a command handler.** If the transaction commits and the Kafka publish fails, the event is lost permanently. The outbox relay is the only component that sends to Kafka.
</Warning>

## Consumer idempotency

Because the relay delivers at-least-once, consumers may receive the same event more than once. Every consumer must be idempotent using the message's `eventId` header:

```sql
CREATE TABLE processed_events (
    event_id     UUID NOT NULL,
    consumer     VARCHAR(100) NOT NULL,
    processed_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (event_id, consumer)
);
```

Claim before processing with an atomic insert-first operation such as `INSERT ... ON CONFLICT DO NOTHING`. If the insert affects zero rows, skip the duplicate message. Do not use `exists` followed by `save`, because concurrent duplicate delivery can pass both checks before either insert commits.

When a consumer has side effects, claim the event and perform the business operation in the same local transaction.
