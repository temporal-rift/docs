## Running tests

Each service builds independently — swap the `-f` path to target `game-service`, `timeline-service`, or
`read-service`. `mvn test` runs unit tests only; integration tests (`*IT`) run under Failsafe via `mvn verify`.

```bash
# All unit tests for one service
mvn -f game-service/pom.xml test

# Single test class
mvn -f game-service/pom.xml test -Dtest="LobbyTest"

# Architecture tests only
mvn -f timeline-service/pom.xml test -Dtest="ArchitectureTest"

# Integration tests, including Modulith/architecture verification (Testcontainers PostgreSQL + Kafka)
mvn -f game-service/pom.xml verify -Dit.test="GameServiceApplicationIT"
mvn -f read-service/pom.xml verify -Dit.test="ReadServiceApplicationIT"
```

## Test categories

| Category | Naming convention | Spring context | Infrastructure |
|---|---|---|---|
| Unit tests | `{Subject}Test` | None | None |
| Slice tests | `{Module}ModuleTest` | `@ApplicationModuleTest` | None |
| Persistence integration tests | `{Subject}PersistenceIT` | `@PersistenceIntegrationTest` (game-service) | Testcontainers PostgreSQL |
| Application integration tests | `{Subject}IT`, including `GameServiceApplicationIT` and `ReadServiceApplicationIT` | `@GameServiceIntegrationTest`, `@TimelineServiceIntegrationTest`, `@ReadServiceIntegrationTest` | Testcontainers PostgreSQL + Kafka |
| Architecture tests | `ArchitectureTest` | None | None |

`game-service` and `read-service` are Spring Modulith applications — their `*ApplicationIT` starts real PostgreSQL
and Kafka via Testcontainers and runs `ApplicationModules.verify()` to assert module boundaries. `timeline-service`
is a plain Spring Boot app (single bounded context, not a Modulith), so its layering is enforced instead by
ArchUnit's `ArchitectureTest` — the same pattern `read-service` also uses alongside its Modulith verification.

### Integration test annotations

Annotate every integration test with its service's composed annotation from the table above. Do not write
`@SpringBootTest` plus an inline `@Import` list: Spring caches one context per distinct combination of test
annotations, and every new combination boots the application and its containers from scratch. A test needing a bean
the annotation does not already provide belongs in that annotation's shared configuration, not in a local import.

<Warning>
**Never hold Testcontainers containers in `static` fields to share them between contexts.** A cached context stays
open for the rest of the JVM with its listeners and schedulers running, so two application contexts sharing one
broker become two members of every consumer group — Kafka gives each partition to exactly one member, so a test's
own events can be delivered to the other context's listeners — and two sharing one database run two schedulers over
the same outbox rows. Only a context with no listeners and no schedulers may share, which is why `game-service`'s
persistence slice can and its application contexts cannot.
</Warning>

## Code quality gates

Both run automatically on every build via the `validate` phase (shown here for `game-service`; the same targets
apply to any service by swapping the `-f` path):

<CodeGroup>
```bash Check formatting
mvn -f game-service/pom.xml spotless:check
```

```bash Fix formatting
mvn -f game-service/pom.xml spotless:apply
```

```bash Checkstyle
mvn -f game-service/pom.xml checkstyle:check
```

```bash Run both
mvn -f game-service/pom.xml validate
```
</CodeGroup>

## Contract publishing

REST and event contracts live in the **`apis`** repo as independently versioned, spec-only Maven artifacts. AsyncAPI
modules (`session-event`, `action-event`, `scoring-event`, `timeline-event`) and OpenAPI modules (`session-api`,
`action-api`, `scoring-api`, `projection-api`) publish the specifications. `temporal-rift-bom` unpacks contract
resources during `initialize` into an artifact-isolated build directory, so services only declare their dependencies and
generate the producer, consumer, or REST-interface artifacts their workflow supports. No service keeps a duplicate
contract copy.

```bash
# 1. Bump version in apis/<module>/pom.xml and merge to main
# GitHub Actions publishes automatically to Maven Central

# 2. After Central publishes it, update the consuming service dependency version and test
mvn -f game-service/pom.xml test
```

<Warning>
**Never use `mvn install` or manually run `mvn deploy` for shared artifacts.** Local publication makes builds
non-reproducible. Merge the version bump to `apis` `main` and let its publishing workflow release the artifact.
</Warning>
