The Simulation Workbench is a separate designer-facing product that runs real game services in isolated lanes. It does not expose its controls to a human-game client and it does not replace the authoritative game rules.

All requests use a JWT bearer token. Reads require `simulation:read`, mutations require `simulation:write`, and an observer replay additionally requires `simulation:observe`. Every mutation has a UUID `Idempotency-Key` header. Repeating a key with the same request returns the original resource; reusing it with a different request returns `409 IDEMPOTENCY_CONFLICT`.

## Discovery

Discovery operations let a designer client find and preview what it can act on without holding identifiers in advance. Reads require `simulation:read`; previewing a manifest requires `simulation:write`. Previewing creates nothing, so it takes no `Idempotency-Key` header.

`previewExperiment` validates a manifest exactly as `createExperiment` does but stores nothing. It returns the `manifestDigest` the manifest would freeze under, the total `caseCount`, a `breakdown` by variant and player count, and a page of `cases` (`caseKey`, `variantLabel`, `seed`, `playerCount`, per-seat `assignments`) in the order and with the case keys the durable run will use. Its query parameters are `limit` (1 to 500, default 100) and `offset`. An invalid or over-bound manifest is `400 INVALID_EXPERIMENT`.

Lists return `{ items, total }` and take `limit` (1 to 500, default 50) and `offset`. Experiments, runs and comparisons are newest first; a run's cases are in matrix order. `listRuns` filters by `experimentId` and `state`; `listCases` by `state` and `variantLabel` and answers `404 RESOURCE_NOT_FOUND` for an unknown run; `listComparisons` by `runId` (baseline or candidate). A case summary carries its identifiers, variant, seed, player count, `state` and a nullable `endReason`. A comparison summary identifies the baseline and candidate sides, the analysis version and seed, and the creation time; `getComparison` returns the computed result. `listPolicies` returns each referenceable bot policy bundle with its `id`, `version`, `artifactDigest`, `description` and accepted `parameters`; a manifest policy built from an entry passes verification.

Guided setup has two more reads. `listLaneBundles` (`GET /api/v1/lane-bundles`) returns one item per distinct pair of effective rules and content digests the lanes serve, busy or free, ordered by those digests. Each item carries the rules and content artifacts, the effective digests, the `services` and `contracts` of the lanes serving it, and `laneCount`; its `rulesArtifact` names the lane's baseline rules document and `effectiveRulesDigest` is that document's digest. It never names a lane, its address, a credential or a bot identity. Without lanes the page is empty. `listExperimentTemplates` (`GET /api/v1/experiment-templates`) returns `baseline-policy-comparison` (one variant; `random` and `faction-greedy`, each on seats 0 to 4) and `rules-variant-comparison` (two variants; `random` on seats 0 to 4). Both default to seeds `["42"]`, player counts `[3, 4, 5]`, every valid faction set, `CYCLIC` rotation, `LOGICAL` time, one concurrent case per lane (from 1 to 64), and the deployment's case timeout and rejected-candidate bound. A client builds the `ExperimentManifest` from a template's defaults, the chosen bundles (the manifest's `services` and `contracts` come from bundles that share them) and the designer's edits. Both reads need `simulation:read`, and an out-of-range `limit` or `offset` on any list returns `400 INVALID_REQUEST`.

## Immutable experiment manifests

Creating an experiment freezes a version-1 manifest. It records variants; resolved rules and content artifact digests; game, timeline, and read service image/source provenance; exact contract versions; policies and their seat assignments; seeds; player counts; faction sets; cyclic seat rotation; logical timing; and execution bounds.

A variant's `rulesArtifact` is its baseline rules document. Optional numeric `overrides` and a `parameterSpaceVersion` express parameter changes instead of a second hand-made bundle; creating the experiment validates those overrides, drops overrides equal to the baseline value, and recomputes the variant's `effectiveRulesDigest`.

Artifact references are portable SHA-256 digests, never credentials or local machine paths. The product retains the resolved artifact bytes. Changing a rule, content bundle, policy, or pinned service revision creates a new experiment; it never modifies a launched manifest.

With all faction sets, cyclic rotations, one seed, two homogeneous policies, and two variants, the matrix contains 220 cases: 55 player-count/faction/seat coordinates per policy/variant. The manifest validates counts from three to five players, unique variant labels, unique seeds, unique factions per set, and positive execution limits before scheduling work.

## Variant rules and parameter spaces

An `EffectiveRules` document has `schemaVersion: 1` and a `properties` object holding every rules property keyed by its full `game.rules.` path. Segments are lowercase kebab-case, except enum-constant map keys, which keep their constant name, and nested maps are flattened with `.`. Values are numbers, booleans, strings, or arrays of those, in served order. Its digest is the lowercase hex SHA-256 of the RFC 8785 canonical JSON serialization of `properties`, so key order and number spelling do not matter: the properties `{"game.rules.probability.amplify-multiplier.II": 2, "game.rules.win-score-threshold": 20}` in either order, with `2` or `2.0`, hash to `2f4e77d6f2f5ad41eb3b05de091e524133995ef6f274a58f539adbf2d5b06fad`.

A variant is a baseline document plus overrides. `parameterSpaceVersion` is required when `overrides` is non-empty, and a supplied `effectiveRulesDigest` that differs from the recomputed value is refused as `400 INVALID_EXPERIMENT`.

`listParameterSpaces` returns every served version ordered by `version`, and `getParameterSpace` returns one, answering `404 RESOURCE_NOT_FOUND` for an unknown version. A parameter space lists `parameters` (`key`, `services`, `baseline`, `min`, `max`, `step`), `derived` (`key` equals `factor × from`), `constraints` (`id`, `expression`, `description`), and `heldFixed` (`key`, `reason`).

`previewVariantRules` applies and validates `rulesArtifact`, `parameterSpaceVersion`, and `overrides` without persisting anything, returning the effective rules, digest, and normalized overrides that freezing would store. `getVariantRules` returns a frozen variant's effective rules, answering `404 RESOURCE_NOT_FOUND` for an unknown experiment or label. A refused override is `400 INVALID_EXPERIMENT` or `400 INVALID_REQUEST` and names the value in `field` plus a `reason`: `UNKNOWN_PARAMETER_SPACE`, `UNKNOWN_BASELINE`, `UNKNOWN_PARAMETER`, `OUT_OF_RANGE`, `OFF_STEP`, or `CONSTRAINT_VIOLATED`; the last also carries `constraintId`.

## Durable runs and cases

A run progresses through `QUEUED`, `RUNNING`, `INTERRUPTED`, `CANCELLING`, `CANCELLED`, `COMPLETED`, or `FAILED`. It reports requested, pending, running, succeeded, failed, and cancelled case counts. Resumption is valid only from `INTERRUPTED`; the retained completed cases remain a single logical sample and are not scheduled again.

Each isolated lane serves one frozen rules and content bundle, and a case plays only on a lane whose effective rules and content digests equal its variant's `effectiveRulesDigest` and `effectiveContentDigest`, so a variant's results always come from its own bundle. A case whose variant's lanes are all busy waits as `PENDING` without holding back the cases of other variants. `startRun` returns `409 MANIFEST_MISMATCH` and creates nothing when some variant of the experiment has no lane serving its bundle at all; the problem `detail` names the label of every such variant.

Each case has a stable case key, a variant, a seed, ordered seat/faction/policy assignments, and its own lifecycle (`PENDING`, `RUNNING`, `SUCCEEDED`, `FAILED`, or `CANCELLED`). Attempts are separately retained with their checkpoint evidence, game identity when present, and failure. A reproduction creates a separate attempt and never adds a research sample. A missing or changed pinned artifact causes `409 MANIFEST_MISMATCH`.

A run keeps its completed results through interruption and cancellation. After an interruption, `resumeRun` schedules only the cases that have no final state, so a case is never counted twice however many attempts recovered it. Cancelling stops scheduling, cancels the pending cases, and lets running cases stop at their next step; every completed result stays readable and the rest are reported as cancelled. Repeating a cancel never reopens a terminal run.

A case succeeds when its game reaches an authoritative ending whose winners, faction reveal, and final scores agree. An ending without winners (`RESOLUTION_FAILED`, `ALL_PLAYERS_ABANDONED`, or `DECK_EXHAUSTED`) is a valid game outcome: the case succeeds with that `endReason`, no winners, and its final scores, and its attempt is not a failure. The winners of `TIMELINE_COLLAPSED` and `TIMELINE_STABILIZED` have no `winType` (`null`); only a normal victory has one.

An attempt fails with `RUNNER_TIMEOUT` when no authoritative ending is reached within the manifest's case limit, `EXECUTION_FAILED` when a lane or service call fails in a way that cannot be reconciled, `CONTRACT_MISMATCH` when a response or policy reference does not match the pinned contracts, `CONFIGURATION_DRIFT` when a service executes another case or manifest than configured, or `POLICY_EXHAUSTED` when a seat has no candidate, pass, or decline left. Timeouts and execution failures are retried on a fresh attempt up to a configured limit; the other failures are deterministic and fail the case at once. A failed attempt is never turned into a game sample.

## Configuration search campaigns

A campaign runs the whole configuration search as one durable resource. `createCampaign` (`POST /api/v1/campaigns`) takes a `CampaignDefinition`: a name; a `baseline` pair of rules and content artifacts; a `parameterSpaceVersion` and `criterionVersion`; at least one policy; unique player counts drawn from 3, 4, and 5; separate `searchMasterSeed` and `confirmationMasterSeed` values; and a `SearchAlgorithm` (`SUCCESSIVE_HALVING_V1` with `initialCandidates`, `screeningSeeds`, `eta`, and `shortListSize`). `budgetSeconds` defaults to 14400 active compute seconds and `parallelism` to 4. The campaign is created in `QUEUED`, starts without another client call, and survives a restart with its budget, state, and log. Equal master seeds are refused.

A `Campaign` returns the frozen definition plus `campaignId`, `state`, `spentSeconds`, `round`, `shortList`, nullable `confirmation` and `failure`, and `createdAt`, `startedAt`, and `finishedAt`. The state is `QUEUED`, `RUNNING`, `PAUSED`, `SEARCH_COMPLETED`, `CONFIRMING`, `COMPLETED`, `CANCELLED`, or `FAILED`; the `shortList` stays empty until `SEARCH_COMPLETED`. `listCampaigns` returns `{ items, total }` newest first and `getCampaign` returns one campaign, both with `simulation:read`; an unknown id is `404 RESOURCE_NOT_FOUND`.

The lifecycle writes need `simulation:write` and an `Idempotency-Key`. `pauseCampaign` is allowed from `QUEUED` and `RUNNING` and moves to `PAUSED`; `resumeCampaign` is allowed from `PAUSED` and moves to `RUNNING`; `cancelCampaign` is allowed from every state except `COMPLETED`, `CANCELLED`, and `FAILED` and moves to `CANCELLED`; `setCampaignParallelism` is allowed from the same states, and its new value applies to the next game started. A write from a state it is not allowed from returns `409 INVALID_CAMPAIGN_STATE`, while repeating a pause, resume, or cancel that already took effect returns the same campaign as a no-op. Games in flight when a campaign pauses finish or are discarded and are never counted twice.

`getCampaignLog` returns `{ items, total }` in decision order. An entry carries `sequence` from 1, `round`, `candidateId`, `overrides`, `effectiveRulesDigest`, the `seeds` played so far, `gamesSpent`, a nullable `evaluation` (`verdict` and `score`), a `decision` (`GENERATED`, `KEPT`, `DISCARDED`, or `SHORT_LISTED`), a nullable `reason` (`GATE_FAILS`, `DOMINATED`, `NOT_IN_TOP_FRACTION`, or `BUDGET_EXHAUSTED`), and nullable `evidence`. The evidence names the failing criterion `lineIds` for `GATE_FAILS` and the `dominatedBy` candidate id for `DOMINATED`.

`startConfirmation` is allowed only from `SEARCH_COMPLETED`, moves the campaign to `CONFIRMING`, and returns `202`. It starts one confirmation run per short-listed candidate and one for the baseline; each run carries `candidateId` (the literal `baseline` for the baseline run), `experimentId`, `runId`, and a nullable `evaluation`. The `CampaignConfirmation` carries `seedCount` (the criterion's `confirmationMinimumSeeds`), `runs`, and `seedOverlap`, which is false for an accepted confirmation. Confirmation seeds derive from `confirmationMasterSeed` only; if any of them already appears in the log's `seeds`, the request returns `409 SEED_OVERLAP` and starts nothing.

An invalid definition returns `400 INVALID_CAMPAIGN` with `field` naming the offending value and a `reason` of `UNKNOWN_PARAMETER_SPACE`, `UNKNOWN_CRITERION`, `UNKNOWN_BASELINE`, `EQUAL_MASTER_SEEDS`, or `INVALID_VALUE`.

## Reports and comparisons

### Reports

`getRunReport` returns the report as JSON, or as CSV with `Accept: text/csv`. It states whether it is complete, the run's case counts (requested, pending, running, succeeded, failed, cancelled), its analysis version and analysis seed, its `formatVersion` (`2`), and a list of cohorts. The version 2 JSON layout is unchanged from version 1 apart from `formatVersion`; the CSV gained the `failureCode` column described below. For every variant, policy, and player count of the run there are four cohort levels:

| Level | `factionSet` | `seatIndex` |
|---|---|---|
| Pooled | `null` | `null` |
| Per seat | `null` | seat |
| Per faction set | set | `null` |
| Per faction set and seat | set | seat |

Only succeeded cases are games. Each cohort reports its own case counts, its eligible games (succeeded cases, each counted once however many attempts it took), and its independent blocks. Pending, running, failed, and cancelled cases appear only in the counts, never in a game metric's denominator, and a report is incomplete while any requested case has not succeeded. A valid ending without winners is still an eligible game.

Every metric names its `statistic` and its `dimensions`:

- `RATE` is the numerator over the denominator, `MEAN` is a total over its sample size, and `QUANTILE` is the smallest observed value whose cumulative share reaches the quantile.
- `dimensions` restricts the metric to a `faction`, `cardType`, `cardGrade`, `specialAction`, `paradoxType`, `endReason`, `quantile`, or `failureCode`; a missing dimension means the metric is not split by it.
- A metric with no eligible data is `NO_DATA` with a null value.

Faction win rate counts the games in which the faction's seat is among the winners, over the eligible games containing that faction. A shared win counts as a win for every winner and also feeds the faction's shared-win rate, so faction rates need not sum to 100%. For example, Erasers present in 10 games and winning 4, one of them shared, have a win rate of 0.4 and a shared-win rate of 0.1.

Card metrics separate cards offered, kept, and played, and measure playability per card and action round. A round the seat did not observe has unknown playability; it is left out of the rate and counted in `unknownCount`. Card and faction associations describe how the run's policies played, not the strength of a card or faction.

Reports of analysis version `2` additionally carry `failure_share` (statistic `RATE`, unit `cases`) in every cohort that pools seats: failed cases with that code over succeeded-or-failed cases, once without a `failureCode` dimension and once per code present. A case's code is the code of its final failed attempt, so a retried attempt that later succeeded does not count; cancelled, pending, and running cases are in neither count. Its interval is the same seed block bootstrap as every other metric.

### Uncertainty

Cases that share a seed share their randomness across faction sets, seat rotations, and variants, so a seed is one independent block. Intervals are 95% percentile intervals from resampling a cohort's seeds with replacement (`BLOCK_BOOTSTRAP`). A cohort with fewer than two seeds reports `INSUFFICIENT_SAMPLE` with its value and no interval. The same analysis version, analysis seed, and case results always reproduce the same report.

### Comparisons

`createComparison` takes a `baseline` and a `candidate`, each a run and one of its variant labels; both may name the same run. The two runs' frozen experiments must be equal in services, contracts, policies and their parameters, seeds, player counts, faction sets, seat rotation, timing mode, and rejected-candidate budget, otherwise the request returns `422 INCOMPARABLE_RUNS` naming each difference. The compared variants' rules and content may differ and are listed in `declaredDifferences`. An unknown run returns `404 RESOURCE_NOT_FOUND`; an unknown variant label or two identical sides return `400 INVALID_COMPARISON`.

A baseline case and a candidate case form a pair when they share seed, player count, policy, and seat-to-faction assignment. In each cohort a seed is a block, and only blocks whose every pair succeeded on both sides enter the paired estimates. Each metric difference reports the baseline value, the candidate value, their difference, and a 95% block-bootstrap interval of the difference. Every pair with a failed or cancelled side (`FAILED_COUNTERPART`) or an unfinished side (`UNFINISHED`) is listed in `excludedPairs`. A comparison is recomputed from current results on every read and stays incomplete while any pair is unfinished or failed.

### Balance criteria and run evaluation

Balance criteria are read-only resources served from the workbench's configuration; a new version is added by configuration, never through the API. `listBalanceCriteria` (`GET /api/v1/balance-criteria`) returns every served criterion version ordered by `version`. `getBalanceCriterion` (`GET /api/v1/balance-criteria/{criterionVersion}`) returns one version; an unknown version is `404 RESOURCE_NOT_FOUND`. A criterion carries its `version`, `digest`, `title`, `analysisVersion`, `lines`, the `WEIGHTED_SUM_OF_SQUARED_DEVIATIONS` aggregation, and the evidence rule. Each line names its `metric`, `derivation` (`DIRECT`, `RATIO_TO_WIN_REFERENCE`, or `SUM_OF_FAILURE_CODES`), `dimension`, `policies`, `playerCounts`, `pooling` (`POOLED` or `PER_FACTION_SET`), `band` (a closed interval, or a one-sided limit with a normalisation `scale`), `role` (`GATE` or `SCORED`), `weight` (positive for scored lines, null for gates), and `rationale`.

`getRunEvaluation` (`GET /api/v1/runs/{runId}/evaluation`) takes a required `variantLabel`, a required `criterionVersion`, and an optional `mode` (`SCREENING` by default, or `CONFIRMATION`). The evaluation is computed from the run's cases on every read with the analysis seed, so the same inputs always return byte-identical documents and nothing is persisted. Every criterion line expands into one evaluated line per cohort and dimension value it covers; the faction ratio and summed failure shares are recomputed in every bootstrap resample. A line `MEETS` when its interval lies inside the band, `FAILS` when it lies wholly outside, and is `INCONCLUSIVE` otherwise (always for `INSUFFICIENT_SAMPLE` or `NO_DATA`); the score is the sum of `weight × deviation²` over the scored lines. Validity comes first: unfinished cases, `CONTRACT_MISMATCH` or `CONFIGURATION_DRIFT` failures, an over-limit `EXECUTION_FAILED` share, or an `ALL_PLAYERS_ABANDONED` game make the evaluation `INVALID` with a null score. A valid evaluation is `REJECTED` when any gate fails; in confirmation mode it is `CONFIRMED` only with a satisfied sample (at least the criterion's minimum seeds over the full case matrix), every pooled gate met, and no scored line failing — otherwise `UNCONFIRMED`, which screening mode always returns. An unknown run, variant, or criterion is `404 RESOURCE_NOT_FOUND`; a missing or invalid parameter is `400 INVALID_REQUEST`. All three reads need `simulation:read`.

### CSV exports

Both CSV exports start with a header row and repeat the full attribution on every row, so a single row stands on its own. A report row holds `formatVersion` (`2`), `runId`, `manifestDigest`, `analysisVersion`, `analysisSeed`, `complete`, the cohort (`variantLabel`, `policyId`, `policyVersion`, `playerCount`, `factionSet` joined with `|`, `seatIndex`), `eligibleGames`, `independentBlocks`, the six case counts, then `metric`, `statistic`, the dimensions (`faction`, `cardType`, `cardGrade`, `specialAction`, `paradoxType`, `endReason`, `quantile`, `failureCode`), `unit`, `value`, `numerator`, `denominator`, `status`, `intervalLower`, `intervalUpper`, and `unknownCount`. `failureCode` follows `quantile`; it is empty for a metric not split by failure code, including the all-codes `failure_share` row, and holds the `AttemptFailureCode` of a per-code `failure_share` row. A comparison row holds `formatVersion` (`1`), `comparisonId`, both sides' run and variant, the analysis version and seed, `complete`, the cohort, `matchedBlocks`, `excludedBlocks`, then `metric`, `statistic`, the dimensions, `unit`, `baselineValue`, `candidateValue`, `difference`, `status`, `intervalLower`, and `intervalUpper`. Comparisons carry no `failure_share`, so their CSV has no `failureCode` column. Empty fields are null values.

## Replay and reproduction

Replay requires `perspective=PLAYER` or `perspective=OBSERVER`. A player replay requires `seatIndex` and returns only that seat's entitled facts at the relevant step; it excludes opposing hidden hands, hidden factions, and future information. An observer replay requires `simulation:observe`, is explicitly separate from player data, and never feeds a policy.

A replay reads the game that counts for the case. Steps are numbered from 0 and keep their number across pages. `afterStep` is the last step already read (omit it to start at the beginning), `limit` caps the page, and `nextStep`, present while more remains, is the `afterStep` that continues the replay. A player replay skips the numbers that belong to other seats. An observer replay lists the steps of every seat and then the raw events (phase `EVENT`) per source in offset order; no order across sources is implied. A player replay without a valid `seatIndex`, or an observer replay with one, is `400 INVALID_REPLAY_PERSPECTIVE`, and an observer replay without `simulation:observe` is `403 INSUFFICIENT_SCOPE`.

Every game a case plays is retained, including failed and abandoned ones. Raw events are deduplicated by source and event identifier, so a redelivered event counts once, and a case whose final score or end-of-game event has not arrived yet stays incomplete instead of being recorded as a zero-score game.

Reproduction runs the exact pinned manifest and accepted transcript again on the lane that played the case, starting from a clean lane state, and decides in every window exactly what the transcript accepted. It has its own reproduction and attempt identifiers and never adds a research sample. It runs only while that lane is free and still serves the case's variant bundle; until then it stays `QUEUED` and is never played on another lane. The response to `reproduceCase` is `202` with state `QUEUED`; repeating the request with the same `Idempotency-Key` returns the same reproduction in its current state, which is how its outcome is read. The state is `QUEUED`, `RUNNING`, `MATCH`, `DIVERGED`, or `FAILED`; on divergence it reports the first semantic step, kind, expected value, and actual value. `FAILED` means the reproduction could not reach an ending and says nothing about the case.

The divergence `kind` is one of `OBSERVATION`, `DECISION`, or `WINDOW` (another seat or window at that step), `MISSING_STEP` or `UNEXPECTED_STEP` (the reproduction stopped early or went on), `UNEXPECTED_WINDOW` (a window the transcript has no decision for), `COMMAND_REJECTED` (the service now refuses a transcript decision), or, after the last step, `END_REASON`, `WINNERS`, `FINAL_SCORES`, `ERAS`, or `SEMANTIC_DIGEST`. Only accepted commands are compared. A case with no saved result or transcript, a pinned artifact that is missing or altered, or a frozen manifest that differs from the one the case ran under returns `409 MANIFEST_MISMATCH`.

## Error codes

The API uses RFC 9457 problem details with a stable symbolic `code`. Unlike the game-platform APIs, workbench codes are symbolic names rather than `<status>-<nn>` values. Validation errors are `INVALID_EXPERIMENT`, `INVALID_REPLAY_PERSPECTIVE`, `INVALID_COMPARISON`, or `INVALID_CAMPAIGN`. A missing or invalid run-evaluation parameter is `400 INVALID_REQUEST`, and an unknown run, variant label, or criterion version is `404 RESOURCE_NOT_FOUND`. `INVALID_EXPERIMENT`, `INVALID_CAMPAIGN`, `MANIFEST_MISMATCH`, and a variant-rule `INVALID_REQUEST` refusal that is attributable to one value also carry `field`, the path of that value (for example `seeds[1]`, `policies[0].seatAssignment[2].seatIndex`, `variants[1].overrides.game.rules.win-score-threshold`, or `confirmationMasterSeed`), so a client can place the problem on the input that caused it. Variant-rule and campaign refusals also carry `reason`; a `CONSTRAINT_VIOLATED` refusal carries `constraintId`, and campaign reasons include `UNKNOWN_PARAMETER_SPACE`, `UNKNOWN_CRITERION`, `UNKNOWN_BASELINE`, `EQUAL_MASTER_SEEDS`, and `INVALID_VALUE`. State and identity errors include `IDEMPOTENCY_CONFLICT`, `EXPERIMENT_IMMUTABLE`, `INVALID_RUN_STATE`, `INVALID_CAMPAIGN_STATE`, `SEED_OVERLAP`, and `MANIFEST_MISMATCH`. `RUNNER_TIMEOUT`, `EXECUTION_FAILED`, `CONTRACT_MISMATCH`, `CONFIGURATION_DRIFT`, and `POLICY_EXHAUSTED` are retained as attempt failures, not reported as normal games.
