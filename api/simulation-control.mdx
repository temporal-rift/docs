---
title: "Simulation Execution Control"
description: "Operator-only per-game execution contexts, deterministic inputs, checkpoints, and logical clock control"
---

Operator-only controls for reproducible execution in isolated simulation deployments. The game, timeline and
read services each expose this contract independently and own their own execution revision and checkpoint. The
caller coordinates the services and downstream projection barriers; an acknowledgement from one service does
not imply global completion. read-service has no timers: advancing its logical clock only moves its logical
time, and a caller is not required to advance it.

A service executes one game per execution context. The operator opens a context carrying that game's effective
rules, plays it, and closes it before opening the next one; no restart is needed between games.

This interface supplies entropy, logical identities, validated faction/seat assignment, and logical time. It
never supplies commands, outcomes, scores, or winner decisions, and its inputs never appear in
participant-facing responses.

## Authorization and deployment boundary

Every operation requires a JWT bearer token carrying the `simulation:control` scope:

```http
Authorization: Bearer <jwt>
```

The routes are registered only in isolated simulation deployments. The first two rows below describe an
isolated simulation deployment; against an ordinary deployment the third row takes precedence for every caller,
because the request never reaches authentication:

| Caller | Result |
|---|---|
| Missing, invalid, or expired token (isolated simulation deployment) | `401` without disclosing execution state |
| Authenticated participant token without `simulation:control` (isolated simulation deployment) | `403 SIMULATION_CONTROL_FORBIDDEN` without disclosing execution context |
| Any caller against an ordinary deployment | `404 SIMULATION_CONTROL_UNAVAILABLE`, even with a control-scoped token |

## Operations

| Operation | Method and path | Success |
|---|---|---|
| Open execution context | `PUT /internal/simulation/v1/execution` | `200` checkpoint |
| Close execution context | `DELETE /internal/simulation/v1/execution?caseKey=` | `204` |
| Read checkpoint | `GET /internal/simulation/v1/checkpoint` | `200` checkpoint |
| Advance clock | `PUT /internal/simulation/v1/clock` | `200` acknowledgement |

## Open execution context

```http
PUT /internal/simulation/v1/execution
```

Opens the execution context for one game with its deterministic inputs and effective rules. The request body is an
`ExecutionContext`; every field is required:

```json
{
  "schemaVersion": 1,
  "caseKey": "6f3f2a52-4f0a-4c69-9a39-2a8f0e2b9d11",
  "seed": "42",
  "entropyVersion": "SHA256_V1",
  "manifestDigest": "64 lowercase hex characters",
  "rules": {
    "schemaVersion": 1,
    "properties": {
      "game.rules.probability.amplify-multiplier.II": 2,
      "game.rules.win-score-threshold": 20
    }
  },
  "rulesDigest": "2f4e77d6f2f5ad41eb3b05de091e524133995ef6f274a58f539adbf2d5b06fad",
  "logicalTime": "2026-10-05T19:00:00Z",
  "seats": [
    { "seatIndex": 0, "playerId": "uuid", "faction": "ERASERS" },
    { "seatIndex": 1, "playerId": "uuid", "faction": "WEAVERS" },
    { "seatIndex": 2, "playerId": "uuid", "faction": "PROPHETS" }
  ]
}
```

- `schemaVersion` is the integer constant `1`.
- `seed` is a decimal string in unsigned 64-bit range (`0` through `18446744073709551615`).
- `entropyVersion` is `SHA256_V1`.
- `manifestDigest` is 64 lowercase SHA-256 hex characters identifying the immutable execution manifest.
- `rules` is the complete effective rules document: `schemaVersion` `1` and every rules property keyed by its full
  `game.rules.` path. Nested maps are flattened with `.`, and values are JSON numbers, booleans, strings, or arrays of
  those in served order. See [Effective rules](#effective-rules).
- `rulesDigest` is the lowercase hex SHA-256 of the UTF-8 bytes of the RFC 8785 (JSON Canonicalization Scheme)
  serialization of `rules.properties`. Key order and number spelling do not matter: `2.0` and `2` give the same
  digest. The example above pairs its rules with their canonical digest.
- `logicalTime` is a UTC date-time.
- `seats` is an ordered array of 3 to 5 entries with contiguous `seatIndex` values starting at `0`, unique
  `playerId` values, and unique factions. Each `faction` is one of `ERASERS`, `PROPHETS`, `REVISIONISTS`,
  `WEAVERS`, or `ACTIVISTS` (see [Factions](/game-design/factions)). Player IDs identify existing authenticated bot
  subjects.

With no context open, the context is accepted, its revision starts at `0`, and its logical time is the context's
`logicalTime`. Opening the same context again is a no-op returning the current checkpoint. Any other context while one
is open returns `409 EXECUTION_CONTEXT_CONFLICT`. With no context open while the service still holds gameplay state of
an earlier context, it opens nothing and returns `409 EXECUTION_STATE_NOT_CLEAN`. A malformed context returns `400
INVALID_EXECUTION_CONTEXT`.

The service validates the rules it uses for this game:

- It recomputes the canonical digest of `rules.properties` and rejects a mismatch with `400
  INVALID_EXECUTION_CONTEXT`.
- Every key must start with `game.rules.`; otherwise the response is `400 INVALID_EXECUTION_CONTEXT`.
- It reads each rule it uses from `rules` and ignores keys it does not use. A missing key, or a value that fails that
  rule's own validation, returns `400 INVALID_EXECUTION_CONTEXT` with `detail` naming the key.

## Close execution context

```http
DELETE /internal/simulation/v1/execution?caseKey=<uuid>
```

Closes the open context for `caseKey` in any state (`READY`, `ACTIVE`, or `TERMINAL`) and answers `204`. On closing,
every pending outbox record, continuation and due timer of that context is discarded and never acts, and the context's
game never changes again. It also discards every other gameplay state of the context, the game's projections and
idempotency claims and the request rate counters of the context's participants, so after a close the service behaves
for the next context exactly as a newly started service. The service then accepts a new context without restarting.

Repeating the close for the most recently closed `caseKey` is a no-op `204`. A `caseKey` that matches neither the open
nor the most recently closed context returns `409 EXECUTION_CONTEXT_CONFLICT`. With no context open and no context ever
closed, the response is `409 EXECUTION_NOT_CONFIGURED`.

## Events of other games

While a context is open, an inbound event whose `gameId` header is not the open context's game is consumed and ignored:
no handler runs. Its offset still advances the `sourceWatermarks` the checkpoint reports. With no context open, every
inbound event is ignored the same way. A late event from a closed game therefore never reaches the next game.

## Read checkpoint

```http
GET /internal/simulation/v1/checkpoint
```

Reads this service's checkpoint. The response is an `ExecutionCheckpoint`:

```json
{
  "caseKey": "uuid",
  "manifestDigest": "64 lowercase hex characters",
  "rulesDigest": "64 lowercase hex characters",
  "revision": 0,
  "logicalTime": "2026-10-05T19:00:00Z",
  "gameId": null,
  "state": "READY",
  "drained": true,
  "outboxPending": 0,
  "continuationsPending": 0,
  "dueTimersPending": 0,
  "nextDeadline": null,
  "sourceWatermarks": [
    { "groupId": "string", "topic": "string", "partition": 0, "nextOffset": 0 }
  ]
}
```

- `rulesDigest` is the digest of the open context's rules.
- `revision` is a service-owned nonnegative integer; each service advances its own revision independently.
- `state` is `READY`, `ACTIVE`, or `TERMINAL`.
- `gameId` and `nextDeadline` are required but nullable.
- `outboxPending`, `continuationsPending`, and `dueTimersPending` are nonnegative counters.
- `sourceWatermarks` are per source/group positions (`groupId`, `topic`, `partition`, `nextOffset`); they do not
  define a global event order.

A drained checkpoint (`"drained": true`) means all work observed up to its listed watermarks has completed. It
does not preclude unseen upstream work from arriving later. A service with no configured execution returns
`409 EXECUTION_NOT_CONFIGURED`.

## Advance clock

```http
PUT /internal/simulation/v1/clock
```

Advances only this service's logical clock. read-service owns no timers, so advancing it only moves its logical
time and a caller is not required to advance it. The request body is a `ClockAdvance`; the response is a
`ClockAcknowledgement`:

```json
{
  "operationId": "uuid",
  "expectedRevision": 0,
  "targetTime": "2026-10-05T20:00:00Z"
}
```

```json
{
  "operationId": "uuid",
  "appliedRevision": 1,
  "logicalTime": "2026-10-05T20:00:00Z"
}
```

- Advancing to the current logical time is a legal idempotent operation; moving backward is rejected with
  `422 CLOCK_REGRESSION`.
- Repeating an `operationId` with the identical body returns its original acknowledgement without another
  advance. Reusing an `operationId` with a different body returns `409 IDEMPOTENCY_CONFLICT`.
- An `expectedRevision` that no longer matches the service's revision returns
  `409 STALE_EXECUTION_REVISION`. Track each service's revision separately.
- A malformed advance returns `400 INVALID_CLOCK_ADVANCE`.

## Coordinating game, timeline, and projection services

One acknowledgement never means the whole simulation has advanced:

1. Open the same execution context on the game service, the timeline service and the read service.
2. Inspect each service's checkpoint separately; revisions, rules digests, states, and watermarks are service-owned.
3. Advance each service that owns timers with its own current `expectedRevision`, then re-read its checkpoint.
   read-service need not be advanced; when it is, only its logical time moves.
4. Wait for downstream projection barriers before treating the step as globally visible; a drained per-service
   checkpoint alone does not imply global completion.
5. When the case ends, close the same `caseKey` on every service before opening the next case's context.

### Effective rules

`EffectiveRules` is the shared `schemaVersion` `1` document with a `properties` object keyed by full `game.rules.`
paths. It is the same document a workbench variant materialises, so a context's rules and a variant's frozen effective
rules are directly comparable by digest. Rule values are JSON numbers, booleans, strings, or arrays of those in served
order; the digest is computed over `properties` only, so key order and number spelling cannot change it.

Execution inputs, seat assignments, and checkpoints stay on this operator interface. Ordinary gameplay keeps
using the participant session, action, scoring, and read APIs, which never expose them.

## Error codes

Errors use RFC 9457 problem details with a required stable string `code`.

| Status | Code | Condition |
|---|---|---|
| `400` | `INVALID_EXECUTION_CONTEXT` | Malformed execution context (for example duplicate factions, gaps in seat indices, an out-of-range seed, a mismatched `rulesDigest`, or a missing or invalid used rule) |
| `400` | `INVALID_CLOCK_ADVANCE` | Malformed clock advance |
| `401` | `AUTHENTICATION_REQUIRED` | Missing, invalid, or expired bearer token |
| `403` | `SIMULATION_CONTROL_FORBIDDEN` | Authenticated caller lacks `simulation:control` |
| `404` | `SIMULATION_CONTROL_UNAVAILABLE` | Control interface not registered in this deployment |
| `409` | `EXECUTION_NOT_CONFIGURED` | No context is open: `getSimulationCheckpoint` and gameplay operations return it. A close returns it only when no context is open and none was ever closed; repeating the most recently closed case key is `204`. |
| `409` | `EXECUTION_CONTEXT_CONFLICT` | A different context is already open, or a close names a case key that matches neither the open nor the most recently closed context once a context has been configured |
| `409` | `EXECUTION_STATE_NOT_CLEAN` | No context is open, but the service still holds gameplay state of an earlier context; nothing is opened, and the caller must close that earlier context before retrying |
| `409` | `IDEMPOTENCY_CONFLICT` | `operationId` reused with a different clock body |
| `409` | `STALE_EXECUTION_REVISION` | `expectedRevision` no longer matches the service revision |
| `422` | `CLOCK_REGRESSION` | `targetTime` precedes the current logical time |
